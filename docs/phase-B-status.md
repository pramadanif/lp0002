## The finding: the guest journal was carrying the member's spending key

SC-B.4 was initially reported green by a test that scanned the journal for the raw 32 bytes of `nsk`.
That scan is a **false negative**: risc0's serde writes each `u8` as its own 32-bit word, so a 32-byte
secret occupies 128 journal bytes and never appears as a contiguous run.

Decoding the journal properly told a different story:

```
raw_nsk=false                        <- what the naive scan saw
word_nsk=true                        <- the same secret, word-encoded
witness_recoverable_from_journal=true
```

The cause: a LEZ program echoes `instruction_data` into the `ProgramOutput` it commits, and the whole
witness was in the instruction. On-chain privacy would have survived — the inner output never reaches
the chain — but the inner receipt would have been a **spending key in a file**.

**Fix.** The instruction was split in two. `ApprovalClaim` (`multisig_id`, `proposal_id`,
`member_root`, `claimed_nullifier` — all public on chain anyway) stays in `instruction_data`.
`ApprovalWitness` (`nsk`, `vpk`, `identifier`, Merkle path) moved to a separate private input, read
after the standard LEZ inputs and never committed. LEZ's caller/callee `instruction_data` match still
holds, because both sides carry the claim.

The split also made proving markedly cheaper, since the witness is no longer serialised into the
journal:

| | Witness in `instruction_data` | Witness as private input |
|---|---|---|
| Proving time | 123.86 s | **53.26 s** |
| Journal size | 5,928 bytes | **776 bytes** |
| `nsk` recoverable from journal | **yes** | **no** |

`the_journal_carries_no_member_secret` now decodes the journal rather than scanning it.
`docs/tried-failed.md` carries the full account, and `docs/security.md` §3b records the residue: the
inner journal still contains the approver's `account_id` via `pre_states` — unavoidable, since that is
how LEZ validates execution — so **inner receipts are prover-local secret material**.

## Two other corrections made this phase

1. **The H8 rationale was wrong** (carried over from Phase A). It claimed that removing the
   account-binding assertion would let a member double-vote by substituting a different `nsk`. It
   would not: the substituted key would also have to be a leaf under `member_root`. Double-voting is
   prevented by the nullifier alone. The assertion buys **liveness**. The design did not change;
   ADR-001 D4 and `docs/tried-failed.md` now say why correctly, and SC-B.5 tests the property that is
   actually at stake.
2. **`prove` was the wrong risc0 feature.** Enabling it compiles Metal kernels on macOS, which needs
   full Xcode — an evaluator on a clean Mac would have hit a build failure instead of a demo. The SDK
   uses risc0's default (client) features and drives the external `r0vm` that `rzup` installs.
